# deed 设计（唯一权威）

版本 2。这份文件定义 deed 是什么、按什么规则运转。代码与它冲突时，改代码。

## 1. 它是什么

deed 是一个工作区的**事实账本**：把"谁说了什么、谁交了哪一版、谁判的、下一步谁动"固定下来，使它不依赖参与者的自觉。

它不持有项目概念。文档契约、测试命令、架构约束、分支规矩属于宿主；deed 只按声明的顺序调用它们、汇总结果、把失败说清楚。

它与规格驱动工具（OpenSpec 一类）的差别不在对象，而在**驱动方式**：规格驱动靠"人记得读文档"，这套东西靠"每轮真的记一笔"。

## 1.1 这些词什么意思

只有一个定义处，就是这张表；文档、命令输出、面板都说这些词，不再另造。

| 词 | 指什么 |
|---|---|
| **账本** | 工作区里的 `.deed/log/*.jsonl`，只能往后加的文件。 |
| **一条记录**／**一行** | 账本里的一行：什么种类、谁记的、什么时候。 |
| **一轮** | 用户与 agent 的一次往返。 |
| **会话** | 一期工作，标签 `S01`：从一个话题开始，到签收或归档结束。 |
| **段** | 一个判决周期，标签 `S01.1`：一批任务一起交付、一起被判。 |
| **任务** | 一件要做的事，标签 `T1`：带「做完的标准」。 |
| **交付记录** | 做完时记下的那句话：做了什么、记的是哪个文件的 sha256。 |
| **撤回** | 交付说错了话时把它退回未做，附一句为什么；账本里两条都在。 |
| **等你定的** | 只有用户能回答的问题，标签 `A1`。 |
| **审查清单** | `deed review` 写出的那份 md：这一段有哪几条、各自的标准与交付记录。 |
| **审查结论** | 审查者读完清单后落的一个判断：放行或打回，附发现。 |
| **放行**／**打回** | 结论的两种；打回要点名哪几条要重做。 |
| **签收** | 用户的一句话：这一期到此为止。 |
| **三种状态** | 讨论、执行、验收。由账本算出来，不是谁按下的按钮。 |
| **下一步** | 现在该谁做什么，只有一处：`deed state`。 |
| **卡住的原因** | 为什么现在轮不到下一步：哪道门没过、欠谁。 |
| **过期** | 记下的 sha256 和工作区里现在的对不上，或清单发出去之后这一段又动了。 |
| **门槛** | 这个工作区的审查要求在账本里的那几条（要不要审、哪些免审、`gates`）。 |

## 2. 六个概念，三层结构

| 概念 | 定义 | 承载 |
|---|---|---|
| **轮次 turn** | 用户与 agent 的一次往返 | 心跳。每轮一条，无条件、与他事无关 |
| **会话 session** | 轮次区间：首轮即开期，签收或强制归档即结束 | 讨论脉络、待裁项、若干段 |
| **段 segment** | 一个判决周期 | 一段独立的任务清单、审查强度、判决结论 |
| **任务 task** | 一件要做的事 | 做完的标准 + 交付记录 |
| **审查 review** | 审查者按清单与角色包判断 | 合格/不合格 + 依据 |
| **签收 sign** | 用户接受"这一期到此为止"并封存会话 | 唯一的正常结束方式 |

状态（讨论 / 执行 / 验收）不是对象，是**算出来的**：由内容推导，不由人设定。

三层各管一件事：会话聚焦"本期所关心的事"，段聚焦"这一批"，任务聚焦"这一件"。视野里只有当前段；历史段收成一行，数据一条不删。

**段不进入讨论态。** 会话的讨论脉络是连续的，不能被段切分；段是讨论中不断切出来的执行单元。

## 3. 三条不变式

1. **规则自己到场**：任何必需动作都不依赖 agent 记得。记轮要有物理钩子（hook），状态要能算出来，会话和段由动作推动。
2. **判与签收分开**：一段的结局由审查者的结论定（pass 封段、fail 点名退回），签收由用户定；人不替审查者审，也不替用户签。系统可以催、可以让代价可见，不能替任何一方下判断。
3. **事实唯一且可追**：同一事实只有一个主人；每个结论都能追到谁、何时、基于什么。

冲突时优先级：2 > 1 > 3。

## 4. 十一条硬规则

1. **首轮即开期**：写入第一条轮次时建立会话（编号按顺序 S01、S02，名字在签收时补），没有"创建会话"这个动作。反过来，**只有轮次能开会话**：会话已收口时，任何其它动作都被拒，不许自己发明一期。
2. **段由判决推进，不许手动切**：当前段被判过后，下一条任务写入时才开新段（惰性）。禁止手动切段——切段会变成逃生舱。
3. **段只封存，不删**：视图重置只发生在"显示什么"，不发生在"数据还在不在"。
4. **待裁项归会话，不归段**：待裁项是"还没定的问题"，跨段存活；处置只有两种——用户裁定（落成任务，进当前段）或 agent 撤回。签收前必须清零。
5. **审查门槛由路径声明，不由感觉**：哪些路径被改就必须过审查，写在宿主的 config 里；内核不猜。任务未声明触及路径时按"需要审查"处理（保守）。路径先归一化（反斜杠转正斜杠、去掉开头的 `./`）；带 `..` 或写成绝对路径的，一律按"要审"处理——不能借路径写法逃出门槛。
6. **先重放，后落盘**：任何写动作先在内存里把账本从头放一遍，放得动才追加这一行。被拒的动作一个字也不进账本，工作区不会因为一次手滑变成重放不了的坏账。
7. **编号与事实不许撞车**：任务与待裁项共用命名空间，同一个会话里 `T1`、`A1` 都不许出现两次；编号由重放后的账本给（取最大值 +1），不由进程各自数。并发写入靠 `.deed/log/lock` 串行。
8. **签收需结清**：当前段已判过、无未做、无做完未判、待裁为零、没有指到工作区外的交付记录，才允许签收。未签收不允许走正常结束；异常结束走强制归档并打标签。
9. **清单与结论成对**：把审查清单发出去这件事本身是账本事实（`review.brief`：路径 + sha256），结论只能回答发出去的那份——没发过清单不许落结论，清单在等回答时被改过、被删掉也不许。手上那份还在等回答，再要一次只是把路径报一遍，不写第二份；上一份已经被回答、被作废、或自己过期了，才另出一份。**清单会过期**：那份发出之后这一段又动了（新交付、或收回了说错的交付），清单上写的就不是现在的事实——这时再要一次会另出一份并说明原因，而不是把「等结论」再说一遍。让人按旧清单落结论，等于让审查者审一件已经变了的事。
10. **交付与判决不共手**：一段里由某个 `by` 交付过任务，就不能用同一个 `by` 落这一段的结论。这是自述身份能撑住的唯一一条独立性：账本不知道"两个不同的人"，只知道"两只不同的手"。硬查换人（每次新审查者）会退化成打卡，不做。
11. **账本不替任何动作填名字**：判决、打回、签收的名字由写者给。以前判决与签收默认写 `by: "user"`，于是交付、判决、签收一条龙跑完，记录上写着是用户按的——那不是"身份是约定"，那是替人签名。现在只有真的在终端里敲（stdin 与 stdout 都是 tty）才允许默认 `user`：那说的是"有个人在键盘前"，不是"这个人是用户"。从管道里跑（agent、CI、测试）必须自己写 `--by`，写了就得认，规则 10 随后就能认出"这只手交付过这一段"。

## 5. 生命周期

```
init（写 config + 记第一轮）
  → 讨论（轮次、范围、待裁项）
  → 段开始（第一条任务写入）
  → 执行（任务：todo → done）
  → 审查（按门槛：审查者拿清单与角色包，落一条结论）
  → 通过 → 段当场封存 → 下次写任务自动开新段
  → 不合格 → 点名退回 → 补完、重新交付、重新审（旧结论作废）
  → 全部结清 → 签收（用户）→ 会话封存 → 自动开新期
```

强制归档（shelve）：未结清而必须放下时使用，打异常标签，不占当前焦点；未结任务持续可见（`deed state` 的"欠着"一行），直到回去结清。

打回之后该段的既有结论作废（被新结论覆盖记 `supersededBy`，被人推翻记 `voidedAt` 与 `voidedBy`），段重新打开；此后再没人审过的那一段**判不动**——不是"没有结论"而是"结论作废"，两者的下一步不同（前者发清单，后者重审）。

## 6. 规则表

**状态怎么算**

| 状态 | 条件 |
|---|---|
| 讨论 | 当前段为空，只有轮次与待裁项 |
| 执行 | 当前段存在未做，或做完未判 |
| 验收 | 当前段已判过、待裁为零，无未做未判 |

**一段怎么结束（审查者封段）**

- 落结论的前提：该段无 todo；发出去的那两份材料还在、字节没动；"这一段最近一次改动"没有晚于发出去那一刻。
  在这之前写的结论回答不了现在的这一段。
- `pass`：该段任务全部转为已交付；段当场封存（`segment.verdict = "pass"`、`judgedAt`、`closedAt`）；下次写入开新段。不需要第二个人再按一次。
- `fail`：必须点名 `--rework T1,T2` 并写 `--why`。被点名的任务退回 todo、交付记录清空；其余保持交付；段不封。
  不点名的结论没人能接，所以被拒。在案的不合格不会被后一条 pass 顶掉——名字上的条目得先重新交付。
- 免审段里若落了不合格结论，同样挡着——结论已经落了，就是事实。
- 记录作废：被新结论覆盖记 `supersededBy`；被人推翻记 `voidedAt` 与 `voidedBy`。都不删行。

**签收（会话级，用户）**

- 当前段已被审查者的 pass 封存；无 todo；无 done 未判；待裁为零。
- 记录用户原话；可同时给会话定名。

**审查门槛**

- **实动清单怎么量**：交付时扫一遍工作区，跟上一次的快照比。跳过 `.deed/.git/node_modules` 一类目录；超过 4 MB 的文件记成 `!size:<字节数>` 而不是跳过——首次出现、或大小变了，它就是改动，任务声明不了它。读不出的文件记 `!unreadable`。**剩下的盲区只有一条**：4 MB 以上文件同尺寸的改内容看不见（这个代价换的是每次交付不必哈希整棵大仓）。
- 门槛是账本事实，不是磁盘文件：`review.required/exempt`、`gates`、面板端口都以 `config.change` 事件写进账本（重放时算成 `doc.config`），`.deed/config.json` 只是它的镜像。规则读算出来的那份，不读文件；两边不一致时 `deed state` 标出来、`deed verify` 报"门槛对不上"并 exit 1。手工改文件改了什么都不算数，收下它要走 `deed init --force --why "为什么改"`——门槛这条预期因此和别的事实一样可追。
- 段内任一任务触及门槛里 `review.required` 的路径，或任一任务未声明路径 → 该段必须审查。
- 全部触及 `review.exempt` 且无未声明 → 免审。
- 审查先发两份材料（`deed review`）：清单 `.deed/review/<段>-<时间戳>.md`（审什么）与角色包 `…-reviewer.md`（怎么审），记一条 `review.brief`：两份路径 + 两份 sha256（`briefDigest`、`guideDigest`）；再由审查者落结论（`deed review --by … --verdict pass|fail`），结论入账的是**发出去那一刻**的这两对路径与指纹。为什么发清单要入账：账本若不知道这份清单存在，就无法说清一份结论读的是哪份；在落结论时才现写一份，记下的永远是审查者没读过的字节。清单不覆写，同一段审两次就有两份，账本记得每次读的是哪一份。账本只记路径与指纹，正文不入账；`deed verify` 重算核对——被改过、丢了、没人发过（结论点名的清单没有对应的 `review.brief`）、目录里躺着没人认领的清单，那一类都不算数（打回或另出一份，再审一次）。
- 门槛读"声明 ∪ 实动"：`task.done` 落盘前先给工作区拍快照、算出这一条改过哪些文件（`changed`），门槛同时看任务声明的路径与这份实动清单。声明写少了逃不出去。
  基线的内容指纹留在 `.deed/workspace.json`（第一次 `task done` 时生成，之后每次交付刷新）；它只是"上一次交付时长什么样"的记录，丢了最多少知道一次动过什么，不丢事实。
- 每条交付记录要么记下一份内容（`--digest <工作区里的普通文件>`），要么就被 `judge`／`sign` 拦下；`deed verify` 把"没记文件"单列一档，不混在"过期"里。

## 7. 动作表

| 动作 | 谁 | 作用 |
|---|---|---|
| `deed init` | 人 | 首次：把门槛写进账本（三条 `config.change` 基线）并记第一轮；`--force` 改门槛要带 `--why`，改动同样记为 `config.change`，文件只是跟着写出来的镜像。收尾把剩下的可选项一次列全（规则、面板、体检、门槛、改门槛，各带命令与去处）——一轮就能做完，不做也不影响判断 |
| `deed init --print-agents` | 人 / agent | 打印一段可粘贴的规则（点明 `deed state` 等命令）；只打印，不建账本、不写工作区 |
| `deed tick` | 任何一轮 / agent | 记一轮（谁、说了什么、做了什么）；只有它能开会话 |
| `deed task add/done/undo/defer/drop` | agent | 任务、交付（done 必须带交付记录）、收回说错的那条交付（undo 带理由，退回未做）、延后、放弃（后两者带理由） |
| `deed ask` | agent | 把模糊需求变成待裁项，必须写清"我理解成什么、为什么不确定" |
| `deed review` | 审查者 | 发两份材料（清单 + 角色包）记 `review.brief`；带 `--by --verdict` 时落结论，回答的是已交出去的那两份。`pass` 直接封段；`fail --rework T1,T2 --why …` 点名退回。交付过这一段的 `by` 不能判这一段 |
| `deed seal` | agent（交付的人） | 封一个免审段：门槛说这一段不用审，于是没有结论可落，但段仍要封——`--why` 写清凭什么不审。它不是结论，签收时这一段会被列成「没经过审查」 |
| `deed judge` | 用户 | `--overturn R1 --why …`：推翻一条结论（签收之前），段回到没判过的样子。`--pass`／`--rework` 已经不再执行（只留读旧账本） |
| `deed sign` | 用户 | 结清并封存会话，自动开新期 |
| `deed shelve` | 用户 | 强制归档，打异常标签 |
| `deed state` | 任意 | 打印当前状态、当前段、下一步·谁 |
| `deed verify` | 任意 | 重算交付记录与清单指纹：交付记录分"路径越界 / 记录过期 / 没记文件"（只核每条的现行交付；同一条路径后来被别人重钉过，就算被覆盖，另报条数），清单分"越界 / 对不上 / 不在了 / 没指纹 / 没人发过 / 没人认领"（不改账本） |
| `deed doctor` | 任意 | 逐行体检账本；坏行指出行号与修法 |
| `deed gate [名字…]` | 人 / 自动 | 按 config 里 `gates` 的顺序跑宿主的门命令，一条不过就停，报名字与退出码 |
| `deed serve` | 任意 | 只读面板（SSE 自刷新） |

没有 `start`、没有 `park`、没有 `back`。会话不由人建，就没有"建"的命令。

**一个参数写两遍就停下问清楚**：`--evidence "…" --evidence "…"` 直接报"只收一个值"，不会悄悄只留最后一条——被丢掉的往往是说话的人以为已经写下的那句。唯一能重复的是 `--finding`：一次结论可以带多条发现，写几条就落几条。

**规则文件不归 deed**：仓库的 `AGENTS.md`（或 `CLAUDE.md`）属于管这个仓库的人，deed 读它、不写它。读出来的结论只有一条——里面有没有 `deed state`；没有就每次 `deed doctor` 提一句、面板顶端挂同一句，直到有人把那段粘进去。这条提示不算坏账，也不改任何事实：账本照样能重放，判断照样出得来。

## 8. 数据形态

**唯一权威是追加账本**：`.deed/log/YYYY-MM.jsonl`，一行一个事件，随工作区提交（它是团队共享的事实）。

**状态是投影**：`deed state` 与面板都从账本即时折算，可随时重算，坏了就删。

理由不是存储偏好，而是不变式 1 的推论：如果状态是一份可变全局文件，agent 每轮都要维护全局一致，整套东西就重新依赖自觉，并发也立刻打架。追加天然廉价、并发安全、可重算。

事件一律带两件事：`at`（UTC 时刻，只来自写入那一刻）与 `s`（落在哪个会话）。开期的那条轮次不带 `s`——它就是这一期的出生证明，指回去会让这一行单独读不懂。

事件类型：`turn`、`task.add`、`task.done`、`task.undo`、`task.defer`、`task.drop`、`ask.raise`、`ask.resolve`、`ask.withdraw`、`review.brief`、`review.log`、`review.overturn`、`segment.seal`、`judge.pass`、`judge.rework`、`sign`、`shelve`、`config.change`。后两个 `judge.*` 只剩读：旧账本里有它们，命令面不再产生（事件含义第 4 版起）。

**每行还带两样东西：`v` 与 `w`。** `v` 是事件含义的版本（`core/events.mjs` 的 `EVENT_VERSION`，现在是 4；加一个事件类型、或改动已有字段的含义，就 +1，同时升 package.json 的 minor），`w` 是写者版本（`transact` 落笔时从 package.json 盖上，`lib/version.mjs` 负责读与比）。分成两个字段只为一件事：读到不认得的类型时，必须能说清是"账本比程序新"还是"这一行坏了"——两者动作相反，前者升级就行、一个字都不能动，后者只能整行挪走。只比 `w` 不够：加了类型却没升版本号时，同版本号的旧程序会把合法的新行判成坏账（真发生过：老进程读到 `task.undo` 就叫人把整行挪去 `rejected`）。`v` 是行自己说的话，比版本号硬。

**身份是约定，不是鉴权**：`who`、`by`、`sign` 记的是自述。账本保证"谁说过什么"可回溯，不保证"说的人是谁"——它不是签名链。

**路径以正斜杠入账**（`core/fold.mjs`，不是 `core\fold.mjs`）：账本会跟着工作区去别的机器。

**一条交付记录里有什么**：一句声明、谁记的、什么时候、记的是工作区里哪个文件（`digestPath`）、那个文件当时的 sha256（`digest`）。
一条任务只有一份**现行交付**——它最后说的那句话。再往前的是历史（谁在哪天说过什么），记下的内容当然会跟着工作区变；那不是过期，是过去。所以「过期 / 越界 / 没记文件」只对现行那份判，早先的只报条数、不挡判决。

后来又有人重钉了同一条路径：新的那句话才代表现在的字节，旧的那句算被覆盖，不算过期——否则文档被后来的任务改一次，所有盯过它的记录都得重交一遍，交的还是假话。

**一条结论会作废，但删不掉**：`fail` 点名的条目退回未做；被人推翻的结论记 `voidedAt`/`voidedBy`/`voidedWhy`，所在段回到没判过的样子（封了的段重新打开）。推翻只在签收之前——签了的那一期是历史，账本不往回改。

**说错了话不靠改写**：`task.undo` 把最后一条交付记录退回未做，撤回的理由留在任务上（`undone`），那条从「现行」退成「撤回过」；账本里两条事实都在，清单的交付记录后面会列出撤回的那条并标明不计。撤回也算账本移动，所以判决前的「结论早于最后一次交付」同样会被撤回触发。

"树变了、记录就过期"是通用做法，保留；一条交付记录是否真的证明事做完了，由宿主的门判断；"它记下的东西还在不在这个工作区里"，由 `verify` 判断。审查清单同理，还多一层：它在账本外、是可被改的普通文件，账本记它发出去时的路径与 sha256（`review.brief`），结论回答的是那条记录；`verify` 对不上就说明这份结论读的不是当初那份，或者那份从来没被交出去过。

**读不懂的两条路，方向相反**：

- 那一行的 `v` 比当前含义版本新 → **账本比 deed 新**。行自己说了它属于更新的一套含义，事实成立，只是这本程序读不懂；升级 deed 就能读。`v` 没超前（或没写 `v`）、而写者版本 `w` 比当前版本新，也是同一个结论。两种都说"账本比 deed 新"，那一行别删也别挪；`doctor`、`state`、`verify`、面板都说这句话，并照旧 exit 1（折不动就是折不动，语义不许猜）。
- 含义版本与写者版本都不超前，却出现陌生类型 → **这一行本来就有问题**（事件类型只增不减，所以旧版本不可能写出当前版本不认识的东西）。这才走唯一的人工修法：`deed doctor` 指出第几行，那一行整行移到 `.deed/log/rejected/` 并记下为什么；其它行一个字不动，缺的那件事用正常命令重做一次。不许手写补账。

## 9. 宿主接口

`.deed/config.json`（写法；真正进规则的是 `deed init` 把它记成的账本门槛）：

```json
{
  "review": { "required": ["src/**", "apps/**"], "exempt": ["docs/**"] },
  "gates": { "commit": ["<命令>"], "check": ["<命令>"] },
  "board": { "port": 7317 }
}
```

deed 对门只做两件事：按顺序跑、把失败说清楚。门的内容属于宿主——它不知道一个门过了意味着什么。

## 10. 已知代价（不掩盖）

1. **滚动速度由用户的判决节奏决定。** 用户不判，段不切，活全压在当前段。这是"判决权不可代理"的代价，系统只能让代价可见（当前段任务数、跨度、未判数）。
2. **审查门槛依赖宿主声明。** 声明写得松，规则就有洞；声明不写时内核保守（要审）。
3. **账本随仓库提交会增长。** 按月分片，一行一轮；这是可追溯的必要成本。
4. **没有跨会话任务池。** 结清前不许换期；必须换期时走强制归档，账留着。
5. **追加要抢锁。** 并发写是串行的：最多等 10 秒，锁里写着持有者的 pid 与开始时间；持有者凭 pid 判活——活着就不夺，死了立刻接手，无 pid 的锁存在超过 250 毫秒才算残留；这是"先重放后落盘"的代价，换来的是账本永远折得动。
6. **坏账不会自愈。** 磁盘被人手改坏之后，deed 只会指出来，不会自动修——因为自动修就得猜哪一行才是真的。
7. **事件类型只增不减。** 要删一种事件，必须同时留下能读旧行的迁移读法，否则旧账本会被判成坏账。加一种事件就是改口径：`EVENT_VERSION` 与 package.json 的 minor 一起 +1——漏了这一步，正在跑的旧程序（版本号一模一样）会把新行当坏账，还建议人把它挪走。
8. **旧账本没有 `w`。** 由 0.2 之前的版本写下的行没有写者版本，读到陌生类型时只能说"没有写者版本"，不能断言是账本新（也不能断言是坏账）——这句话是诚实的代价。
9. **清单是文件，不是签名。** 账本记审查清单发出去时的路径与 sha256，能说清一份结论对得上哪一份；它不知道那份清单是谁写的——发出去之后谁都能改，改了只能被 `verify` 发现，发现之前不算数。

## 11. 不做与暂不做（附触发条件）

**MCP 服务：不做。** 判断标准只有一条——**这个协议有没有多产出一条事实**。MCP 只换一条送达的路：命令已经能在任何会跑命令的宿主里用，做成工具只是让它多一个入口。入口一多，规则就得跟着两边维护，"事实唯一"当场破；换来的是常驻进程、多工作区下的实例路由、工具 schema 与账本事件名的漂移——每一样都要有人长期记着。AOCI-CODE 同时写 AGENTS.md 又注册 MCP，正说明工具面解决的是"能不能调"，不解决"知道按什么来"。

暂不做，等这三条同时成立再说：

1. 出现**跑不了命令**的宿主（纯对话窗口、只有工具调用的沙箱），届时 MCP 是唯一的送达方式；
2. 命令表已经收敛成一个唯一源，工具 schema 从那源里生成，不手写第二份；
3. 有人愿意承担常驻进程的运维（起停、端口、多工作区隔离）。

真做的时候只做只读四件：`state`、`verify`、`doctor`、`gate`。写入一律走命令——那才留得下"谁在什么时候敲的"。

**其它明确不做的：**

- **导出任务清单/验收清单成文件**：它们是账本此刻算出来的，导出只会多一份会过期的副本。要给别人看，给 `deed state` 的输出。落到账本外的只有一件东西必须记指纹——审查清单：它要交给账本外的审查者、会被改。
- **"每次审查都换人"**：身份是自述，硬查换人只会变成换个字符串的打卡。能查的那一半已经做了（规则 10）。
- **自动派活**：谁来做下一件事属于宿主，deed 只输出"下一步 · 谁 · 命令"。派活接不上时由 `doctor` 明说未接，不假装。
- **面板上的时钟**：只有 `doctor` 读一次本机时钟算"账本冷了多久"，且只说差值不做判定；`fold` 与面板渲染永远不碰时钟，否则同一份账本会渲染出两种字节。

## 12. 下一版要改的（已定，未实现）

这一节记的是已经谈定、还没写进代码的形状。实现一条就删掉那一段——"已定未做"留在文档里超过一轮，就是文档在撒谎。

### 12.1 一期要有一句目的

会话要有 `goal`：一段话，说清这一期要做成什么。落在账本里（`goal.set`，可以改，改一次一条记录，旧的留着）。

三个读者：面板顶部、每份审查清单的开头、签收时的比对对象——签收签的是账本里那一刻的目的。

它不是开工的门槛：没有目的也能记轮次、立任务、开段。它是收口的条件：出整体审的清单之前必须有目的（`deed review --all` 在缺目的时停下，说"先说清这一期要做成什么"）。

### 12.2 清单只有一个文件：`.deed/plan.md`

`deed plan` 从账本生成草稿，人和 agent 直接改这个文件，`deed submit` 一次性落账。清单是一份随时可读的文件，所以标记做完、撤回、放弃都写在文件里——没有一条命令是"改清单"的。

```
# 这一期要做成什么
一句话或一段话。

## 段 S01.1
- [x] T1 标题
  标准：做完的标准
  交付：跑了什么，结果几比几
- [ ] T2 标题
  标准：…
- ? 还没编号的条目
  标准：…
~~ T3 不做了
  理由：为什么不做
```

规则：

- **勾上 = 交付**：`[x]` 必须带一行 `交付：`，说的是"跑了什么、结果几比几"——这一行机器猜不出来，只能人写；其余由 `submit` 自己算（碰了哪些文件、每份内容的 sha256）。
- **取消勾选 = 撤回**：`[x]` 改回 `[ ]` 并写 `理由：`，最后那条交付退回未做，撤回的理由留在条目上。说错了话就把勾去掉，别把话说圆。
- `?` = 新条目，`submit` 时领号。
- `~~` = 放弃（有"做到什么时候"的落延后），必须写理由。
- 已有的条目消失、又没有 `~~`：整批拒——少一条只能是有人写了不做，不能是打字打掉了。
- 整批原子：任何一行不合格，整批都不落，报行号与原因。半份清单进账本比没进更坏。
- 命令面收缩：`task add/done/undo/defer/drop` 撤掉，清单上的一行就是一次动作。旧账本照读——读的是事件，不是命令。

### 12.3 一条交付记录带多份文件指纹，而且不用人写

一半已经实现：一条交付可以钉多个文件（`--digest` 写几遍，落在 `evidence.files: [{path, digest}]`，旧账本的单 `path`/`digest` 照读），`verify` 逐份核对，哪份变了就点名哪份。

还没实现的是"不用人写"：`submit` 落账时应当从工作区快照的前后差自己算出碰过哪些文件、各是什么 sha256，而不是等人挑几份来钉。清单上因此也不再有"路径：""文件："两行——一边是人的预期，一边是系统看得见的事实，让人手抄一遍只是形式，抄漏了反而变成假事实。

### 12.4 要不要审：不猜目录名

系统不预设任何目录名。判断只用两种东西：

- 工作区自己声明过的路径（门槛里的必审 / 免审）——声明是工作区的事实，不是内核的常识；
- 数得出来的规模：这次交付碰了几个文件、几个字节、跨了几个顶层目录。

规则：声明必审的路径 → 审；碰的文件数超过 N（默认 5）→ 审；字节数超过 M（默认 20000）→ 审；跨了三个以上顶层目录 → 审；全在免审路径且规模都不触发 → 免审；剩下的（没声明、没碰文件）→ 审。

新工作区的 `init` 不替人猜名字：门槛里只写"什么都还没声明"，于是全部要审，`doctor` 提示一句"要免审就把路径写进门槛"。deed 自己的仓库把它自己的 `core/ cli/ lib/ board/` 写进自己的门槛——那是它自己声明的，不是内核给的。

复杂度算不出来。工具只能把"看起来很小"的挑出来免掉，剩下的都审——判断留给审查者。

### 12.5 谁判：审查者封段，人签收

- `review.log` 的 `pass` 直接封段，不再需要第二个人 `judge --pass`。
- `fail` 带 `--rework T1,T2 --why "…"`：一条记录同时给结论和点名，被点名的条目回未做，段重新打开。
- `judge` 只剩 `--overturn`：人推翻一条结论，必须写为什么。它是例外，不是步骤。
- 窗口在签收之前：签了就是历史，账本不往回改——错在哪就开新一期把要补的记进去。
- 不动的那条：交付过这一段的人不能判这一段；要审的段每条现行交付都记了 sha256。

### 12.6 整体审

对象是一期，不是一段：清单覆盖所有段的任务，开头是目的，后面是各段结论、延后与放弃的条目。

- 单段的一期：不另做段审，整体审就是它——通过同时封段、允许签收。同一份材料审两遍是浪费。
- 多段的一期：先每段封，最后整体审。
- 会过期：结论早于这一期最后一次改动，就不算数。
- 只挡签收，不挡执行：整体审没过，仍然可以继续做下一条。

### 12.7 审查者拿到的是两份东西

- 清单（审什么）：目的、任务与标准、现行交付与记下的 sha256、各段结论。
- 角色包（怎么审）：先读标准再读代码；不信交付记录，逐条复跑；每条标准给"达成 / 未达成 / 无法判断"；主动往边界和失败路径上探；发现写成"结论 + 为什么 + 证据在哪 + 怎么改"。

两份一起交给审查者。派给谁由人决定，账本只保证事后能查到结论是谁落的。

### 12.8 规则只加在看得见的那一半

一条规则该不该加，看的不是"内部又多了几条"，而是"用户的下一屏会不会变"：每做完一条，清单上就勾上；没经过审查，就不算做完；每次交互，账本里多一轮；下一步永远只有一句；交付之后再动，结论自己会红。

不改变任何可观察行为的规则，不加。

### 12.9 实现顺序

1. **先说清谁判、怎么审**（12.5、12.6）：一旦定成「审查者封段、人只推翻」，后面两条才有落点。
2. **再改规则**（12.4）：要不要审取决于工作区自己声明的路径与数得出来的规模；它决定 12.5 里「免审段」长什么样。
3. **最后改接口**（12.2、12.3）：清单收成一个文件、`submit` 一次落账并自己算 sha256。接口最后改，因为它要长在前面两条定好的形态上。

12.1 是目的，不动；12.7、12.8 跟着 12.5 一起落。
