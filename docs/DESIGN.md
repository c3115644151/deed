# deed 设计（唯一权威）

版本 2。这份文件定义 deed 是什么、按什么规则运转。代码与它冲突时，改代码。

## 1. 它是什么

deed 是一个工作区的**放行协议**：谁有资格说「这件事过去了」、要凭什么、下一步谁动。底座是一份只能往后加的记录，产品是记录之上那套会拒绝人的规则——它不依赖参与者的自觉。

它不持有项目概念。文档契约、测试命令、架构约束、分支规矩属于宿主；deed 只按声明的顺序调用它们、汇总结果、把失败说清楚。

它与规格驱动工具（OpenSpec 一类）的差别不在对象，而在**驱动方式**：规格驱动靠"人记得读文档"，这套东西靠"每轮真的记一笔"。

## 1.1 这些词什么意思

只有一个定义处，就是这张表；文档、命令输出、面板都说这些词，不再另造。

| 词 | 指什么 |
|---|---|
| **账本** | 工作区里的 `.deed/log/*.jsonl`，只能往后加的文件。 |
| **一条记录**／**一行** | 账本里的一行：什么种类、谁记的、什么时候。 |
| **一轮** | 用户开口的那一次往返。agent 自己做了什么不算一轮（那是交付记录与结论里的事）。 |
| **会话** | 一期工作，标签 `S01`：从一个话题开始，到签收或归档结束。 |
| **期** | 一次会话（标签 `S02`）：从一句话开始，到签收或归档结束。 |
| **段** | 一批一起交付、一起被判的任务，标签 `S02.1`；审查的对象就是这个整体。 |
| **子段** | 段里的再分（尚未实现）：一段太长、要分批送审时才切。现在不出现这个词，出现时也只表示「段里面的批」。 |
| **整体审** | `deed review --segment S0x.N`：回答**一整段**的标准够不够得上——这是段这一层的审查。它之上还有一层期审（下面那一格），再往上才是签收。 |
| **签收** | 人的一句话：这一期到此为止。它不做审查，只在条件都满足时把这一期合上：每一段都有结局、没有未做的、没有已交付未判的、没有待裁的、这一期的期审已经通过。 |
| **任务** | 一件要做的事，标签 `T1`：带「做完的标准」。 |
| **交付记录** | 做完时记下的那句话：做了什么、动了哪些路径（只记路径与字节数，不记文件内容）。 |
| **撤回** | 交付说错了话时把它退回未做，附一句为什么；账本里两条都在。 |
| **等你定的** | 只有用户能回答的问题，标签 `A1`。 |
| **审查清单** | `deed review` 写出的那份 md：这一段有哪几条、各自的标准与交付记录。 |
| **审查结论** | 审查者读完清单后落的一个判断：放行或打回，附发现。放行要逐条给判定（达成／未达成／无法判断）。 |
| **冻结** | 清单发出去、还没被回答的这段时间，这一段不收文件改动：交付、撤回一条交付都不收（新活落进下一段）；记轮次、写题、延后、放弃、改到下一段照收。冻结只拦写的一侧，账本里已经落下的行一律照读。 |
| **撤回清单** | `deed review --segment S0x.N --withdraw --why "…" --by "谁"`：这一份不作数，段回到执行态。撤回是作者的动作，账本留着谁、为什么。 |
| **段审**／**期审** | 段审：`deed review --segment S0x.N` 回答一段（段是批），一直交给同一个人（清单写明 `by`，结论由他落）。期审：`deed review --all` 在每段都有结局之后判这一期做成的样子与各段之间说不说得通，每次都换一个人。签收在期审之后。 |
| **放行**／**打回** | 结论的两种；打回要点名哪几条要重做。 |
| **关闭这一段** | 这一段的结局：审查者放行，或审查设置说不用审时 `deed seal` 记下凭什么不审。关闭之后这一段不再收新活、不再改。 |
| **未结项** | 关掉之前还不清的东西：延后、放弃、没经过审查的段。签收可以带着它们走，但它们要写清是什么。 |
| **记账** | 一条记录写进账本的那一刻。账本只往后加，所以记错了的账只能用后来的记录改口。 |
| **改到下一段** | 清单上的一行：这一段已经有交过的活、正要送审，还没动手的活跟着这一行挪到下一段。 |
| **三种状态** | 讨论、执行、验收。由账本算出来，不是谁按下的按钮。 |
| **下一步** | 现在该谁做什么，只有一处：`deed state`。 |
| **卡住的原因** | 为什么现在轮不到下一步：哪一条检查没过、谁还没结。 |
| **过期** | 清单发出去之后这一段又动了（新交付、或收回了说错的交付）：那份清单写的已经不是现在的事实。 |
| **审查设置** | 这个工作区的审查要求在账本里的那几条：哪些路径必须审、哪些免审、多大的改动算大、`gates` 跑哪些命令。 |

## 2. 六个概念，三层结构

| 概念 | 定义 | 承载 |
|---|---|---|
| **轮次 turn** | 用户与 agent 的一次往返 | 心跳。每轮一条，无条件、与他事无关 |
| **会话 session** | 轮次区间：首轮即开期，签收或强制归档即结束 | 讨论脉络、待裁项、若干段 |
| **段 segment** | 一个判决周期 | 一段独立的任务清单、审查强度、判决结论 |
| **任务 task** | 一件要做的事 | 做完的标准 + 交付记录 |
| **审查 review** | 审查者按清单与角色包判断 | 合格/不合格 + 依据 |
| **签收 sign** | 用户接受"这一期到此为止"并封存会话 | 唯一的正常结束方式 |

状态（讨论 / 执行 / 验收）不是对象，是**算出来的**：由内容推导，不由人设定。

三层各管一件事：会话聚焦"本期所关心的事"，段聚焦"这一批"，任务聚焦"这一件"。视野里只有当前段；历史段收成一行，数据一条不删。

**段不进入讨论态。** 会话的讨论脉络是连续的，不能被段切分；段是讨论中不断切出来的执行单元。

## 3. 三条不变式

1. **规则自己到场**：任何必需动作都不依赖 agent 记得。记轮要有物理钩子（hook），状态要能算出来，会话和段由动作推动。
2. **审查、判决、签收三件事分开**：审查者判这一段通不通过（pass 把它交回来，fail 点名退回）；这一段过不过由用户判（面板上「判决通过」），关闭是那一刻；签收是用户收这一期。三层各按各的，系统可以催、可以让代价可见，不能替任何一方下判断。
3. **事实唯一且可追**：同一事实只有一个主人；每个结论都能追到谁、何时、基于什么。

冲突时优先级：2 > 1 > 3。

## 4. 十三条硬规则

1. **首轮即开期**：写入第一条轮次时建立会话（编号按顺序 S01、S02，名字在签收时补），没有"创建会话"这个动作。反过来，**只有轮次能开会话**：会话已结束时，任何其它动作都被拒，不许自己发明一期。
2. **段由判决推进，清单可以预先排**：当前段被判过后，下一条任务写入时才开新段（惰性）。清单里写好几节 `## 段` 就是预先排：一节一个段，空标题的那一节 submit 时领号并落一条 `segment.plan`，排在后面；同一时刻只有「排在最前、还没关闭、也不是清单排出来的」那一段收活（`takingSegment`），其余段只记条目——交付与送审当场拒，并说清现在收活的是哪一段；它接过活的条件只有一条，前面那段关闭了。禁止手动切段——切段会变成逃生舱。新活与 `task.carry`（清单上一行 `改到下一段：`）都落进「最后一个未关闭的段」：清单排好了就落那儿，没排时 `改到下一段` 当场拒（先在清单里加一节），新条目则自己开一段。这一段一条都没交过时，改到下一段等于原地不动，命令当场拒并说清该怎么办。这条判断在重放里做，不在命令里：`segmentOf` 看最末那一段有没有还在等回答的 `review.brief`，有就不往里塞新活，新条目自己开下一段。一次改段开出来却没接住活的那个空段不算一段。只在 `submit` 里挡不够——账本里照样会多出一行落在旧段的任务，重放出来的段就不是「一起被审的那一批」了。
3. **段只封存，不删**：视图重置只发生在"显示什么"，不发生在"数据还在不在"。
4. **待裁项归会话，不归段**：待裁项是"还没定的问题"，跨段存活；处置只有两种——用户裁定（落成任务，进当前段）或 agent 撤回。签收前必须清零。
5. **审查审查设置由路径声明，不由感觉**：哪些路径被改就必须过审查，写在宿主的 config 里；内核不猜。任务未声明触及路径时按"需要审查"处理（保守）。路径先归一化（反斜杠转正斜杠、去掉开头的 `./`）；带 `..` 或写成绝对路径的，一律按"要审"处理——不能借路径写法逃出审查设置。
6. **先重放，后落盘**：任何写动作先在内存里把账本从头放一遍，放得动才追加这一行。被拒的动作一个字也不进账本，工作区不会因为一次手滑变成重放不了的坏账。
7. **编号与事实不许撞车**：任务与待裁项共用命名空间，同一个会话里 `T1`、`A1` 都不许出现两次；编号由重放后的账本给（取最大值 +1），不由进程各自数。并发写入靠 `.deed/log/lock` 串行。
8. **签收需结清**：每一段都有结局（审查者的放行，或 `deed seal` 记下凭什么不审）、无未做、无做完未判、待裁为零、没有指到工作区外的交付记录、**这一期的期审已经通过**，才允许签收。签收不做审查：审查分两层，段审判这一段，期审判这一期做成的样子——签收只是把这一期合上。没经过审查的段不会被悄悄放过——签收那一刻它们连同理由一起摊开。未签收不允许正常结束；异常结束走强制归档并打标签。
9. **清单与结论成对**：把审查清单发出去这件事本身是账本事实（`review.brief`：清单与角色包两份路径），结论只能回答发出去的那份——没发过清单不许落结论，清单在等回答时被改过、被删掉也不许。手上那份还在等回答，再要一次只是把路径报一遍，不写第二份；上一份已经被回答、被作废、或自己过期了，才另出一份。**清单会过期**：那份发出之后这一段又动了（新交付、或收回了说错的交付），清单上写的就不是现在的事实——这时再要一次会另出一份并说明原因，而不是把「等结论」再说一遍。让人按旧清单落结论，等于让审查者审一件已经变了的事。
10. **交付与判决不共手**：一段里由某个 `by` 交付过任务，就不能用同一个 `by` 落这一段的结论。这是自述身份能撑住的唯一一条独立性：账本不知道"两个不同的人"，只知道"两只不同的手"。硬查换人（每次新审查者）会退化成打卡，不做。
11. **账本不替任何动作填名字**：判决、打回、签收的名字由写者给。以前判决与签收默认写 `by: "user"`，于是交付、判决、签收一条龙跑完，记录上写着是用户按的——那不是"身份是约定"，那是替人签名。现在只有真的在终端里敲（stdin 与 stdout 都是 tty）才允许默认 `user`：那说的是"有个人在键盘前"，不是"这个人是用户"。从管道里跑（agent、CI、测试）必须自己写 `--by`，写了就得认，规则 10 随后就能认出"这只手交付过这一段"。
12. **送审即冻结，挡住的是文件改动**：清单发出去、还没被回答的这段时间，这一段不能再被换掉审查者手上的东西——交付、撤回一条交付都不收；新活落进下一段。记录层面照旧：记轮次、写题、延后、放弃、改到下一段都收，它们是决定不是字节。要改这一段的活，先 `--withdraw` 撤回这份清单。落结论不比字节：这一段在审时作者改不动它；别处动了盘不归账本管，账本只记路径。清单每份都列全部条目——「判过了、这次不再判」实测一次都没用上，删了。**冻结只拦写的一侧**：这一条在落盘前一刻判（`cli/session.mjs` 的 `refuseFrozen`），账本里已经落下的行一律照读——重放不因为这一段后来送了审，就把早先那一条交付判成坏账。

13. **段审一直用同一双手，期审每次换一双手**：一段的清单第一次交给谁（`review.brief.by`），之后这一段的清单与结论都归他——同一段的判断不该每轮换个人从头摸一遍（段审的对象是同一个体，只有期审每次单开）。期审反过来要求一双手没判过这一期的任何一段、也没期审过这一期：它判的是各段之间的一致性，判过段的人来判这一期，等于自己给自己加的那套判断背书。
14. **期审判的不是段审的汇总**：它回答的是这一期做成的样子对不对、各段之间说不说得通——不重判段里的条目。`deed review --all` 的清单列的是目的、各段结局、这一期定下的边界与弃、还挂着的东西；`fail` 点名的是段号，被点名的段重新打开（条目保持交付），由原来那双手再判一次。
## 5. 生命周期

```
init（写 config + 记第一轮）
  → 讨论（轮次、范围、待裁项）
  → 段开始（第一条任务写入）
  → 执行（任务：todo → done）
  → 审查（按审查设置：审查者拿清单与角色包，落一条结论）
  → 通过 → 段当场封存 → 下次写任务自动开新段
  → 不合格 → 点名退回 → 补完、重新交付、重新审（旧结论作废）
  → 段都关了 → 条件都满足 → 签收
  → 全部结清 → 签收（用户）→ 会话封存 → 自动开新期
```

强制归档（shelve）：未结清而必须放下时使用，打异常标签，不占当前焦点；未结任务持续可见（`deed state` 的"还没结"一行），直到回去结清。

打回之后该段的既有结论作废（被新结论覆盖记 `supersededBy`；旧账本里「被人推翻」的记 `voidedAt` 与 `voidedBy`，含义第 22 版起不再产生），段重新打开；此后再没人审过的那一段**判不动**——不是"没有结论"而是"结论作废"，两者的下一步不同（前者发清单，后者重审）。

## 6. 规则表

**状态怎么算**

| 状态 | 条件 |
|---|---|
| 讨论 | 当前段为空，只有轮次与待裁项 |
| 执行 | 当前段存在未做，或做完未判 |
| 验收 | 当前段已判过、待裁为零，无未做未判 |

**一段怎么结束（审查通过，由用户判决关闭）**

- 落结论的前提：该段无 todo；发出去的那清单与角色包还在、字节没动；"这一段最近一次改动"没有晚于发出去那一刻。
  在这之前写的结论回答不了现在的这一段。
- `pass`：审查者说的是"这一段通得过"。这一段**不关闭**——它记下 `verdict = "pass"`、`reviewedAt`、`reviewedBy`，
  交回给用户；此后它不再收新活（新写的开下一段），交付与撤回交付照样冻结。含义第 22 版及以前的行按当时的样子读：
  那时 pass 就是关闭，拿今天的规矩重放旧账本会把已经发生过的事判成没发生。
- 判决：用户在面板上按「判决通过」，落一条 `verdict.pass`（`by`、`via:"panel"`），这一段此刻才关闭
  （`judgedAt`、`closedAt`），段里的已交付转为"已收下"。判决只有一个方向：过不过由人不按来回答，
  系统不替他判，也不给"判决不通过"——审查者那一层已经有打回。
- `fail`：必须点名 `--rework T1,T2` 并写 `--why`。被点名的任务退回 todo、交付记录清空；其余保持交付；这一段不关闭。
  不点名的结论没人能接，所以被拒。在案的不合格不会被后一条 pass 顶掉——名字上的条目得先重新交付。
- 免审段里若落了不合格结论，同样挡着——结论已经落了，就是事实。
- 记录作废：被新结论覆盖记 `supersededBy`；被人推翻记 `voidedAt` 与 `voidedBy`。都不删行。

**期审（会话级，审查者）**

- 什么时候有：段都关了、无 todo、无 done 未判。期审清单 `.deed/review/<期>-period-<时间戳>.md` 列的是这一期的目的、各段的结局、这一期定下的边界与弃、还挂着的东西——不列段里的条目。
- 谁判：一双手，且这一期里没判过任何一段、也没期审过这一期（规则 13）。清单记下它交给谁（`review.brief.by`），结论要由同一双手落。
- `pass`：这一期做成的样子成立，下一步才轮到签收。`fail`：点名段号（`--rework S01.7`）并写 `--why`；被点名的段重新打开，原先那条段结论作废（留史），条目保持交付。
- 期审清单发出之后，任何一段又落了结论或又被打开，这份清单就旧了；另出一份（下一次换一双手）。

**签收（会话级，用户）**

- 每一段都有结局（审过并由用户判决关闭，或免审由 `deed seal` 封）；无 todo；无 done 未判；待裁为零；这一期的期审已通过。
- 签收不做审查：段的判断在段里做，整期的判断在期审里做，这里只是把这一期合上（含义第 20 版起期审是账本事实；更早那些整期上的结论是当年的"签收核对"，照读成历史，不添门也不挡签收）。
- 记录用户原话；可同时给会话定名。

**审查审查设置**

- **实动清单怎么量**：交付时扫一遍工作区，跟上一次的快照比。跳过 `.deed/.git/node_modules` 一类目录；超过 4 MB 的文件记成 `!size:<字节数>` 而不是跳过——首次出现、或大小变了，它就是改动，任务声明不了它。读不出的文件记 `!unreadable`。**剩下的盲区只有一条**：4 MB 以上文件同尺寸的改内容看不见（这个代价换的是每次交付不必哈希整棵大仓）。
- 审查设置是账本事实，不是磁盘文件：`review.required/exempt`、`gates`、面板端口都以 `config.change` 事件写进账本（重放时算成 `doc.config`），`.deed/config.json` 只是它的镜像。规则读算出来的那份，不读文件；两边不一致时 `deed state` 标出来（「审查设置 文件与账本不一致」）。手工改文件改了什么都不算数，收下它要走 `deed init --force --why "为什么改"`——审查设置这条预期因此和别的事实一样可追。
- 段内任一任务触及审查设置里 `review.required` 的路径，或任一任务未声明路径 → 该段必须审查。
- 规模也算一条：这次交付碰的文件超过 5 个、称出来的字节超过 20000、跨了超过两个顶层目录（即三个以上）→ 一律要审。文件数与顶层目录数从交付记录里数得出来，字节是交付那一刻称的（`task.done.bytes`，工作区差里那些路径都称）。交付自己记下、却没称过字节的文件算「说不清多大」，一律要审——免审是给数出来确实很小的改动留的，不是给说不清的；只声明过、这次没交付到的路径不算，路径本身已经把话说了。删掉的文件也在这条里：它原来多大，交付那一刻已经称不出来，记成 0 字节就等于说「删掉三十 KB 不算大」，所以删过的路径不进 `bytes`，按要审算。审查设置里写 `review.size` 可以改这三个默认值。`segment.seal` 封过的段不再重算规模：那是账本上写下的决定，后来的规则收紧改不了它。被审查者 `pass` 封的段照样重算（`needsReview` 对它仍会回答），但结局由结论决定——`reviewState` 看的是有没有一份有效的 `pass`，重算出来的重量不会把审过的段翻成「该审而没审」。
- 声明与规模都不触发，且全部触及 `review.exempt` → 免审。
- 审查先出清单与角色包（`deed review`）：清单 `.deed/review/<段>-<时间戳>.md`（审什么）与角色包 `…-reviewer.md`（怎么审），记一条 `review.brief`：两份路径（`brief`、`guide`），并在 `.deed/tmp/<段>-<时间戳>/` 开一个临时区给审查者做实验（结论落地时连里面的东西一起删掉）；**清单在等回答期间这一段冻结**（详见规则 12）：不能交付、不能撤回交付；记轮次、写题、放弃照旧；要改这一段的活先 `--withdraw` 撤回；再由审查者落结论（`deed review --by … --verdict pass|fail --result T1=met`）：pass 要求这一段每条都有判定，判定按条记进 `results`（每条只留 `id`、`verdict`、`note`）。结论回答的是**发出去那一刻**那两份文件。为什么发清单要入账：账本若不知道这份清单存在，就无法说清一份结论读的是哪份；在落结论时才现写一份，记下的永远是审查者没读过的字节。清单不覆写，同一整体审两次就有两份，账本记得每次读的是哪一份。账本只记路径，正文不入账；清单丢了、或结论点名的清单没有对应的 `review.brief`，那个结论不算数（另出一份再审）。
- 审查设置读"声明 ∪ 实动"：`task.done` 落盘前先给工作区拍快照、算出这一条改过哪些文件（`changed`），审查设置同时看任务声明的路径与这份实动清单。声明写少了逃不出去。
  基线（上一次交付时各路径的大小）留在 `.deed/workspace.json`（第一次 `task done` 时生成，之后每次交付刷新）；它只是"上一次交付时长什么样"的记录，丢了最多少知道一次动过什么，不丢事实。
- 每条交付记录要么指着工作区里至少一个动过的路径，要么就被 `sign` 拦下（「这些交付没记下任何文件」）。

| `deed task add/done/undo/defer/drop` | agent | 旧接口，仍能用（清单的一行就是它的一次调用）；新工作区用 `deed plan` + `deed submit` |
| `deed ask` | agent | 把模糊需求变成待裁项，必须写清"我理解成什么、为什么不确定" |

| `deed shelve` | 用户 | 强制归档，打异常标签 |

| `deed panel` | 任意 | 看面板在不在：不在就用后台进程拉起来（URL 打在输出里），`--stop` 立即停。每条命令执行前都探测一次，30 分钟没人连就自己退；`DEED_NO_PANEL=1` 一条都不起。面板不写账本 |

没有 `start`、没有 `park`、没有 `back`。会话不由人建，就没有"建"的命令。

**每个动词收哪些开关只有一处写着**：`cli/spec.mjs` 的表。解析与 `--help` 都从它出，所以帮助和解析不会说两套话；不认的开关直接拒，并猜一个最接近的（`--criterias` → `--criteria`），被拼错的开关不会悄悄变成"这个动作没带这个参数"。

**一个参数写两遍就停下问清楚**：`--evidence "…" --evidence "…"` 直接报"只收一个值"，不会悄悄只留最后一条——被丢掉的往往是说话的人以为已经写下的那句。唯一能重复的是 `--finding`：一次结论可以带多条发现，写几条就落几条。

**规则文件不归 deed**：仓库的 `AGENTS.md`（或 `CLAUDE.md`）属于管这个仓库的人，deed 读它、不写它。读出来的结论只有一条——里面有没有 `deed state`；没有就每次 `deed doctor` 提一句、面板顶端挂同一句，直到有人把那段粘进去。这条提示不算坏账，也不改任何事实：账本照样能重放，判断照样出得来。

## 8. 数据形态

**唯一权威是追加账本**：`.deed/log/YYYY-MM.jsonl`，一行一个事件，随工作区提交（它是团队共享的事实）。

**状态是投影**：`deed state` 与面板都从账本即时折算，可随时重算，坏了就删。

理由不是存储偏好，而是不变式 1 的推论：如果状态是一份可变全局文件，agent 每轮都要维护全局一致，整套东西就重新依赖自觉，并发也立刻打架。追加天然廉价、并发安全、可重算。

事件一律带两件事：`at`（UTC 时刻，只来自写入那一刻）与 `s`（落在哪个会话）。开期的那条轮次不带 `s`——它就是这一期的出生证明，指回去会让这一行单独读不懂。

事件类型：`turn`、`task.add`、`task.done`、`task.undo`、`task.defer`、`task.drop`、`task.carry`、`ask.raise`、`ask.resolve`、`ask.withdraw`、`goal.set`、`review.brief`、`review.log`、`review.overturn`、`segment.seal`、`judge.pass`、`judge.rework`、`sign`、`shelve`、`config.change`。后两个 `judge.*` 只剩读：旧账本里有它们，命令面不再产生（事件含义第 4 版起）。`goal.set` 是这一期要做成什么的一句话，可以改，改一次就是账本上的一次（事件含义第 5 版起）；`review.brief` 与 `review.log` 都带 `scope`：`segment`（默认，看一段）或 `session`（看一期的各段）。**第 9 版起签收核对的 `rework` 写的是段号**（`S02.3`）——它手上就是各段的结论，段里哪一条不行由那一段点名；第 9 版之前那种行点的是条目，按当时的写法读，不拿今天的口径重判历史。**第 10 版起有 `task.carry`**：一段送审之后不再收新活，没做的条目靠它改到新开的那一段——放弃说的是「不做了」，写不成「换个时候做」。**第 13 版起交付记录带 `run`**：交付时真跑过的那条命令、退出码与它报的条数；旧行没有这一格，读成没跑过。**第 12 版起轮次只记人开口的那一轮**：`turn` 的 `who` 只认 `user`，agent 的进展不进轮次；旧账本里 agent 自记的行照读，只是不再算一轮——那是它当时记下的自述，不是讨论。

**第 11 版起这条判断在重放里做**：最末那一段手上还有没人回答的 `review.brief` 时，新条目自己开下一段——`segmentOf` 按行上的 `v` 判，老账本按当时的样子重放（拿新规矩重排，历史里写死的段号会被判成坏账）。

**每行还带两样东西：`v` 与 `w`。** `v` 是事件含义的版本（`core/events.mjs` 的 `EVENT_VERSION`，现在是 15；加一个事件类型、或改动已有字段的含义，就 +1，同时升 package.json 的 minor），`w` 是写者版本（`transact` 落笔时从 package.json 盖上，`lib/version.mjs` 负责读与比）。分成两个字段只为一件事：读到不认得的类型时，必须能说清是"账本比程序新"还是"这一行坏了"——两者动作相反，前者升级就行、一个字都不能动，后者只能整行挪走。只比 `w` 不够：加了类型却没升版本号时，同版本号的旧程序会把合法的新行判成坏账（真发生过：老进程读到 `task.undo` 就叫人把整行挪去 `rejected`）。`v` 是行自己说的话，比版本号硬。

**身份是约定，不是鉴权**：`who`、`by`、`sign` 记的是自述。账本保证"谁说过什么"可回溯，不保证"说的人是谁"——它不是签名链。

**账本层不重查审查设置**：`core/fold.mjs` 只拒绝自相矛盾的事件——封一个还有没交付的段、判一个已经判过的段、点名跨段的重做、认不出的类型；它不重新回答「这一段当年该不该审」。审查设置写在账本里（`config.change`），历史行只能按它写的那一刻重放：拿今天的审查设置去核当年的 `segment.seal`，会把合法历史判成坏账。该审的段不能被封，这条由命令入口挡（`deed seal` 先过 `sealBlockers`，审查设置说要审的段封不了）；挡的是人，不是账本。手改账本文件永远可能——那属于「不许做」，不属于「挡得住」。

**路径以正斜杠入账**（`core/fold.mjs`，不是 `core\fold.mjs`）：账本会跟着工作区去别的机器。

**一条交付记录里有什么**：一句声明、谁记的、什么时候、记的是工作区里哪些文件（`files: [{path}]`，旧行里带的 `digest` 照读不照写）、那次交付真动过哪些路径（`changed`）、各多大（`bytes`）、跑过哪条命令与它报的条数（`run: { command, exit, tests, pass, fail }`，第 13 版起；命令不报条数时三个数留 `null`——「没有数」与「数对不上」是两件事）；一批 `submit` 落的几条还带同一个 `batch: { at, size }`——它们共用一次工作区差，分不出哪条改了哪份；`size` 是这一批落了几条，写死在账本里，所以撤回其中一条之后仍说得出原本几条。
新账本还多两样：`files`（这次交付动过的每个路径）与 `bytes`（每个路径交付那一刻有多大）。字节不是给人看的，是让"这次改动小到不用审"能被数出来（事件含义第 6 版起）。
一条任务只有一份**现行交付**——它最后说的那句话。再往前的是历史（谁在哪天说过什么），记下的内容当然会跟着工作区变；那不是过期，是过去。所以「过期 / 越界 / 没记文件」只对现行那份判，早先的只报条数、不挡判决。

后来又有人重新记了同一条路径：新的那句话才代表现在的字节，旧的那句算被覆盖，不算过期——否则文档被后来的任务改一次，所有盯过它的记录都得重交一遍，交的还是假话。

**一条结论会作废，但删不掉**：`fail` 点名的条目退回未做；旧账本里「被人推翻」的结论记 `voidedAt`/`voidedBy`/`voidedWhy`，照读成历史（含义第 22 版起这个动作不再产生）。签了的那一期是历史，账本不往回改。
在案的不合格挡住后面的 `pass`：它点名的条目既没重新交付、也没被放弃，`pass` 落不下来，报"还没结清"。交付结清的是"改好了"，放弃结清的是"这件事改主意不做了"——两条都在账本里，后一条带着理由，所以都算数。落 `pass` 时会把"被点名但已放弃"的条目逐个印出来，下一个读账本的人知道那笔账是怎么了的。查的是**在案那条**记录说了什么，不是新来的那条带着几版——每行都是最新版，拿版本号当闸门等于没有闸门。旧账本里有点名之前写下的不合格：没有可结清的条目，于是它永久挡着 `pass`，出路只有人推翻（`judge --overturn`）。这不是陷阱：不点名的不合格本来就没说清要改什么，谁也不能替它宣布已经改完。

**数与期望当场核**：交付记录里那个「几比几」不是从我这里抄进账本的，`deed submit --run "<命令>"` 真跑一遍，退出码与 `tests/pass/fail` 记进 `run` 那一格；记录里与总条数同一分母的数对不上，整批拒（抄上一轮的数就是这个后果）。说得出现象的，配一行 `期望：<命令> => 要看到的话`，记账前真跑：跑不出来就是假记录——这比事后被审查者对出来便宜，也比让审查者去替机器核数公平。两样都没配的交付，清单上标成「只是说法」：那句话可以是真的，但这一份账里没有东西能核它。

记账前后各核一次字节：量差之后、记账之前重算一遍每条交付要记的路径，变了就整批拒（这一处能真拒，抛在 build 里一条都不落）；记账之后立刻再核一遍，变了只能说、只能撤回——它已经在账本里了，说成没发生才是谎。窗口只剩记账那一瞬，用例盯的是那条判断本身。

**说错了话不靠改写**：`task.undo` 把最后一条交付记录退回未做，撤回的理由留在任务上（`undone`；事件含义第 8 版起还带 `undoes`：被撤那条记下的路径），那条从「现行」退成「撤回过」；账本里两条事实都在，清单的交付记录后面会列出撤回的那条并标明不计。撤回也算账本移动，所以判决前的「结论早于最后一次交付」同样会被撤回触发。**撤回也能撤一条放弃**（事件含义第 15 版，`MEANING.dropBack`）：落在一条放弃/延后上的 `task.undo` 撤的是它此刻的效力，任务回到未做、`revived` 里记下走过这一遭——放弃错了只有新开一条的话，账本里的错口径会一直挂着，而新开的那条说的又是同一件事。被撤那条当时指着哪个文件（`undoes`：路径）跟着撤回一起入账——不然撤完之后，除了记录自证，没有东西能说清撤的是哪一条。两条入口写的是同一个事实：`deed task undo`，和清单里把勾去掉再加一行 `理由：` 交给 `deed submit`；只有一条写了，等于停在半路上。

"树变了、记录就过期"是通用做法，删了：它把「文件后来被别人改过」算成别人的错，而账本从来只记路径。一条交付记录是否真的证明事做完了，由宿主的门判断。审查清单同理：它在账本外、是可被改的普通文件，账本记它发出去时的两份路径（`review.brief`），结论回答的是那条记录；清单丢了、或没有对应的 `review.brief`，那个结论不算数。

**读不懂的两条路，方向相反**：

- 那一行的 `v` 比当前含义版本新 → **账本比 deed 新**。行自己说了它属于更新的一套含义，事实成立，只是这本程序读不懂；升级 deed 就能读。`v` 没超前（或没写 `v`）、而写者版本 `w` 比当前版本新，也是同一个结论。两种都说"账本比 deed 新"，那一行别删也别挪；`doctor`、`state`、面板都说这句话，并照旧 exit 1（折不动就是折不动，语义不许猜）。
- 含义版本与写者版本都不超前，却出现陌生类型 → **这一行本来就有问题**（事件类型只增不减，所以旧版本不可能写出当前版本不认识的东西）。这才走唯一的人工修法：`deed doctor` 指出第几行，那一行整行移到 `.deed/log/rejected/` 并记下为什么；其它行一个字不动，缺的那件事用正常命令重做一次。不许手写补账。

## 9. 宿主接口

`.deed/config.json`（写法；真正进规则的是 `deed init` 把它记成的账本审查设置）：

```json
{
  "review": { "required": ["src/**", "apps/**"], "exempt": ["docs/**"] },
  "gates": { "commit": ["<命令>"], "check": ["<命令>"] },
  "board": { "port": 7317 }
}
```

deed 对门只做两件事：按顺序跑、把失败说清楚。门的内容属于宿主——它不知道一个门过了意味着什么。

## 10. 已知代价（不掩盖）

1. **滚动速度由用户的判决节奏决定。** 用户不判，段不切，活全压在当前段。这是"判决权不可代理"的代价，系统只能让代价可见（当前段任务数、跨度、未判数）。
2. **审查审查设置依赖宿主声明。** 声明写得松，规则就有洞；声明不写时内核保守（要审）。
3. **账本随仓库提交会增长。** 按月分片，一行一轮；这是可追溯的必要成本。
4. **没有跨会话任务池。** 结清前不许换期；必须换期时走强制归档，账留着。
5. **追加要抢锁。** 并发写是串行的：最多等 10 秒，锁里写着持有者的 pid 与开始时间；持有者凭 pid 判活——活着就不夺，死了立刻接手，无 pid 的锁存在超过 250 毫秒才算残留；这是"先重放后落盘"的代价，换来的是账本永远折得动。
6. **坏账不会自愈。** 磁盘被人手改坏之后，deed 只会指出来，不会自动修——因为自动修就得猜哪一行才是真的。
7. **事件类型只增不减。** 要删一种事件，必须同时留下能读旧行的迁移读法，否则旧账本会被判成坏账。加一种事件就是改口径：`EVENT_VERSION` 与 package.json 的 minor 一起 +1——漏了这一步，正在跑的旧程序（版本号一模一样）会把新行当坏账，还建议人把它挪走。
8. **旧账本没有 `w`。** 由 0.2 之前的版本写下的行没有写者版本，读到陌生类型时只能说"没有写者版本"，不能断言是账本新（也不能断言是坏账）——这句话是诚实的代价。
9. **清单是文件，不是签名。** 账本记审查清单发出去时的两份路径，能说清一份结论对得上哪一份；它不知道那份清单是谁写的，也不对它的内容——发出去之后谁都能改，账本只保证「结论回答的是这条记录」。

## 11. 不做与暂不做（附触发条件）

**MCP 服务：不做。** 判断标准只有一条——**这个协议有没有多产出一条事实**。MCP 只换一条送达的路：命令已经能在任何会跑命令的宿主里用，做成工具只是让它多一个入口。入口一多，规则就得跟着两边维护，"事实唯一"当场破；换来的是常驻进程、多工作区下的实例路由、工具 schema 与账本事件名的漂移——每一样都要有人长期记着。AOCI-CODE 同时写 AGENTS.md 又注册 MCP，正说明工具面解决的是"能不能调"，不解决"知道按什么来"。

暂不做，等这三条同时成立再说：

1. 出现**跑不了命令**的宿主（纯对话窗口、只有工具调用的沙箱），届时 MCP 是唯一的送达方式；
2. 命令表已经收敛成一个唯一源，工具 schema 从那源里生成，不手写第二份；
3. 有人愿意承担常驻进程的运维（起停、端口、多工作区隔离）。

真做的时候只做只读三件：`state`、`doctor`、`gate`。写入一律走命令——那才留得下"谁在什么时候敲的"。

**其它明确不做的：**

- **导出任务清单/验收清单成文件**：它们是账本此刻算出来的，导出只会多一份会过期的副本。要给别人看，给 `deed state` 的输出。落到账本外的只有一件东西必须记下路径——审查清单：它要交给账本外的审查者。
- **"每次审查都换人"**：身份是自述，硬查换人只会变成换个字符串的打卡。能查的那一半已经做了（规则 10）。
- **自动派活**：谁来做下一件事属于宿主，deed 只输出"下一步 · 谁 · 命令"。派活接不上时由 `doctor` 明说未接，不假装。
- **面板上的时钟**：只有 `doctor` 读一次本机时钟算"账本多久没动"，且只说差值不做判定；`fold` 与面板渲染永远不碰时钟，否则同一份账本会渲染出两种字节。

## 12. 形状与进度

这一节记的是谈定过、但行为还没整段写进正文的形状。实现之后**标题就标「已实现 · 见 §x」**，正文以那一节为准，这里只留形状；"已定未做"留在文档里超过一轮，就是文档在撒谎。

### 12.1 一期要有一句目的（已实现 · 见 §7 `deed goal`、§8 `goal.set`）

会话要有 `goal`：一段话，说清这一期要做成什么。落在账本里（`goal.set`，可以改，改一次一条记录，旧的留着）。

三个读者：面板顶部、每份审查清单的开头、签收时的比对对象——签收签的是账本里那一刻的目的。

它不是开工的审查设置：没有目的也能记轮次、立任务、开段。它是结束的条件：签收签的就是账本里那一刻的那句话——没有它，那句话也就没有什么可比的了。

### 12.2 清单只有一个文件：`.deed/plan.md`（已实现 · 见 §7 `deed plan`／`deed submit`）

`deed plan` 从账本生成草稿，人和 agent 直接改这个文件，`deed submit` 一次性记账。清单是一份随时可读的文件，所以标记做完、撤回、放弃都写在文件里——没有一条命令是"改清单的某一条"。

```
# 这一期要做成什么
一句话或一段话。

## 段 S01.1
- [x] T1 标题
  标准：做完的标准
  交付：跑了什么，结果几比几
- [ ] T2 标题
  标准：…
- ? 还没编号的条目
  标准：…
~~ T3 不做了
  理由：为什么不做
```

规则：

- **勾上 = 交付**：`[x]` 必须带一行 `交付：`，说的是"跑了什么、结果几比几"——这一行机器猜不出来，只能人写；其余由 `submit` 自己算（碰了哪些文件、各多大）。
- **取消勾选 = 撤回**：`[x]` 改回 `[ ]` 并写 `理由：`，最后那条交付退回未做，撤回的理由留在条目上。说错了话就把勾去掉，别把话说圆。
- `?` = 新条目，`submit` 时领号。
- `~~` = 放弃（有"做到什么时候"的落延后），必须写理由。
- 已有的条目消失、又没有 `~~`：整批拒——少一条只能是有人写了不做，不能是打字打掉了。
- 整批原子：任何一行不合格，整批都不落，报行号与原因。半份清单进账本比没进更坏。
- 命令面收缩：`task add/done/undo/defer/drop` 撤掉，清单上的一行就是一次动作。旧账本照读——读的是事件，不是命令。

实现补上的、形状里没写的几件事：

- **领到的号写回清单**：`?` 在 `submit` 时领 `T` 号，记账后清单被重写成带号的样子（`- [ ] T17 标题`）。不写回去，下一次 `submit` 会把它当成又一条新条目。
- **改标题、改标准都整批拒**：账本里已有的条目在清单上换了个标题或换了一套标准，会被拒——还没有 `amend`，改了就是要开一条新条目，旧的留着。
- **清单本身不进工作区快照**：它在 `.deed/` 里，不在工作区；所以"这次交付碰了哪些文件"不会被清单自己带脏。
- **清单的每一节就是一个段**：空标题的节 submit 领号（`segment.plan`），写了段号的节直接落那一段；收活只有一段——排在前面的段判过、关闭之后，后面那段才接过活（判 `takingSegment`：未关闭且不是清单预排的那一段）。
- **清单里写着哪一节，不等于新条目落进那一段**：一段送审、还在等结论时它不再收新东西（§6 规则 2）。草稿这时会在末尾多印一节 `## 下一段（S0x.N 在等结论…）`，写在那里的 `?` 落进下一段（§6 规则 2）；这一段没有送审时草稿不多印这一节，`?` 就落在它自己身上。落进哪一段由账本说得算，`deed submit` 在领号那一行把它印出来（`写进清单 · T17 · S02.19 · 标题`）——文件里的位置只是给人读的。

### 12.3 一条交付记录带多份文件，而且不用人写（已实现 · 见 §8「一条交付记录里有什么」）

一条交付记多份文件：`evidence.files: [{path}]`——只记路径，不记内容；旧账本里那些 `digest` 字段照读，不再写新的。

`submit` 走的是"不用人写"那条：记账时从工作区快照的前后差自己算出碰过哪些文件，也一并称出字节数（要不要审的规模规则用它）。工作区差里那个已经不在的路径不称：它没有今天的重量，原来多重也回不去了。清单上因此没有"路径：""文件："两行——一边是人的预期，一边是系统看得见的事实，让人手抄一遍只是形式，抄漏了反而变成假事实。

基线只在**真交付**的那一批里推进：一次只加条目、只领号、只撤回的 `submit` 不刷新它（否则它把工作区里等着被交付的改动吃掉，下一条交付看起来什么都没动——那不是干净，是丢数据）。

一次 `submit` 落了多条交付时，工作区只量了一次差：改动的归属是**整批**，不是其中某一条。账本把这件事写在 `task.done.batch = { at, size }` 上（同一批共用这一批的时刻，`size` 是这一批原本几条——撤回一条也不改它），清单里每条下面写一行"同批交付：这一批共 N 条（其中 M 条已撤回）"——三条一字不差的记录不再让人以为各自记下了各自的东西。要按条目分开归属，就一条一条交（`deed task done`）。

### 12.4 要不要审：不猜目录名（已实现 · 见 §6「要不要审」三条）

系统不预设任何目录名。判断只用两种东西：

- 工作区自己声明过的路径（审查设置里的必审 / 免审）——声明是工作区的事实，不是内核的常识；
- 数得出来的规模：这次交付碰了几个文件、几个字节、跨了几个顶层目录。

规则：声明必审的路径 → 审；交付记下却没称过字节的文件 → 审；动过却没重量的路径（删掉的东西）→ 审；碰的文件数超过 N（默认 5）→ 审；字节数超过 M（默认 20000）→ 审；跨了三个以上顶层目录 → 审；全在免审路径且规模都不触发 → 免审；剩下的（没声明、没碰文件）→ 审。

新工作区的 `init` 不替人猜名字：审查设置里只写"什么都还没声明"，于是全部要审，`doctor` 提示一句"要免审就把路径写进审查设置"。deed 自己的仓库把它自己的 `core/ cli/ lib/ board/` 写进自己的审查设置——那是它自己声明的，不是内核给的。

复杂度算不出来。工具只能把"看起来很小"的挑出来免掉，剩下的都审——判断留给审查者。

规模那三条已经写进 `needsReview`，§6 与这一节说的是同一句话：字节由 `task.done.bytes` 在交付那一刻称，文件数与顶层目录数从路径数出来，默认值 5／20000／两个顶层目录（跨三个以上就要审）。

一条线和一条边界：**`deed seal` 封过的段不再重算规模**。那是账本上写下过的决定（`segment.seal` 带着 `--why`），后来把审查设置写细——比如补上「没称过字节的按要审算」——不回头改写它。否则一次收紧就能把先前「全部免审」的一期重新算成要审，而签收时又写着那几段「没经过审查」，两句话互相打脸。`needsReview` 对 `segment.seal` 封过的段直接返回 false——判的是 `sealedBy` 与 `closedAt` 两个都**是真值**（账本上真写下过一次封存），不是一句 `why`，也不是「这个字段存在就算」；`reviewState` 与面板的段标签跟着它。半个封存（`sealedBy` 有名字、`closedAt` 没有或为空）不算封过，照常按审查设置重算。**这个形状不是手改账本才有的**：签收核对判不合格、把一条写在 `deed seal` 封过的段里的任务点回来时，那一段会被重新打开——`sealedBy` 留着，`closedAt` 清成 `null`（`core/fold.mjs` 的 fail 分支）。它每天都会发生，所以守卫按「两个都在」读，重算出来的结论与段已经重新打开这件事一致。

被审查者 `pass` 封的段没有这道豁免：它照常按今天的审查设置重算（一段 90KB 的交付会算出「要审」）。这不影响结局——`reviewState` 认的是那份有效的 `pass`——但如果有人拿 `needsReview` 的返回值去问「这一期还没结什么」，会读到一条与结局无关的「是」。要读结局，读 `reviewState` 和 `signBlockers`。


### 12.5 谁判：审查者判通不通过，用户判这一段过不过，签收收这一期（已实现 · 见 §6「一段怎么结束」、§4 规则 9 与 10、§7 `deed review`／面板）

- `review.log` 的 `pass` 只说明"审查通得过"：段留在手上，等用户判决（`verdict.pass`）才关闭。
- `fail` 带 `--rework T1,T2 --why "…"`：一条记录同时给结论和点名，被点名的条目回未做，段重新打开。
- 没有「推翻结论」这个动作：结论判错由审查机制自己回答（另出一份清单重判），人不需要改审查者的判。含义第 22 版起账本不收这一行。
- 判决只有一个方向（过）；它与签收是两处、两个时刻：判决按段，签收按期。
- 窗口在签收之前：签了就是历史，账本不往回改——错在哪就开新一期把要补的记进去。
- 不动的那条：交付过这一段的人不能判这一段；要审的段每条现行交付都指着至少一个路径。

### 12.6 签收不做审查（已实现 · 见 §4 规则 8、§6「签收（会话级，用户）」）

审查只在段里做：每一段由它自己的结局关闭——审查者的放行，或 `deed seal` 记下凭什么不审。
签收是人的一句话，它不做判断，只看条件：每一段都有结局、没有未做的、没有已交付未判的、
没有待裁的、没有指到工作区外的交付记录。条件齐了，签收就把这一期合上。

- 整期上没有第二份结论可落（含义第 18 版起，`scope:"session"` 的 `review.log`／`review.brief`
  写不进新账本）。旧账本里落过的照读成历史，不添门、不挡签收。
- 没经过审查的段不会被悄悄放过：签收那一刻，它们连同「凭什么不审」一起列出来。
- 前一段通过就是前一段的结局，不是后一段的门；最后一段通过时，下一步直接是签收。

### 12.7 审查者拿到的是两份东西（已实现 · 见 §6「审查先出清单与角色包」那句）

- 清单（审什么）：目的、任务与标准、现行交付动过的路径、各段结论。
- 角色包（怎么审）：先读标准再读代码；不信交付记录，逐条复跑；每条标准给"达成 / 未达成 / 无法判断"；主动往边界和失败路径上探；发现写成"结论 + 为什么 + 依据在哪 + 怎么改"。

两份一起交给审查者。派给谁由人决定，账本只保证事后能查到结论是谁落的。

### 12.7.1 三个闸：只有面板能写（已实现 · 含义第 21 版）

页面上只有人能按的那几处：验收屏写原话按「签收这一期」（议题通过那一层还没做，闸在、没有东西可放）。其余一律只读。

- 命令行那条路关了：`deed sign` exit 1，只回一句指到面板的话，一个字不记账。`deed judge` 这个动词整个不在了（推翻结论不是人要做的事）。
- 按钮只在条件满足时出现：签收要 `signBlockers` 为空。
- 唯一写入口是 `POST /gate`：只收 127.0.0.1、只收同源（没有 `Origin` 或与 `Host` 一致），别的 POST 一律 405。
- 落下的行带 `by` 与 `via:"panel"`（旧账本里这两行没有 `via`，照读）；面板与命令行走同一个 `lib/record.mjs`——重放、校验、追加一处。
- 不是因为「命令更严格」，而是因为账本要分得开「人按的」与「程序跑的」：两者落款的来源不同，事后才查得出是谁放的行。

### 12.8 规则只加在看得见的那一半

一条规则该不该加，看的不是"内部又多了几条"，而是"用户的下一屏会不会变"：每做完一条，清单上就勾上；没经过审查，就不算做完；每次交互，账本里多一轮；下一步永远只有一句；交付之后再动，结论自己会红。

不改变任何可观察行为的规则，不加。

### 12.9 实现顺序

1. **先说清谁判、怎么审**（12.5、12.6）：一旦定成「审查者关闭这一段、人只签收」，后面两条才有落点。
2. **再改规则**（12.4）：要不要审取决于工作区自己声明的路径与数得出来的规模；它决定 12.5 里「免审段」长什么样。
3. **最后改接口**（12.2、12.3）：清单收成一个文件、`submit` 一次记账并自己算碰了哪些路径。接口最后改，因为它要长在前面两条定好的形态上。

12.7、12.8 跟着 12.5 一起落了；12.1 与 12.6 也落了（见各自标题）。
## 13 体检层：这个工作区还是不是一个项目

系统里有两层判断，各自的输入不同：

- **规则**（`core/rules.mjs`）：读账本，回答"下一步谁动"。
- **体检**（`core/checks.mjs`）：读账本 **和盘上的目录快照**，回答"这个工作区还是不是一个项目、差在哪几条"。

体检是**纯函数**：同样的账本 + 同样的目录快照，永远得到同样的结论。目录由调用者先取（`lib/tree.mjs`），检查层不自己去读盘。
它**不产生事实、不产生行动**：只给状态与诊断。行动仍由规则给，规则可以读诊断，于是"下一步"能说出"先补哪一条"。

### 13.1 这张表是机制登记处

`CHECKS` 是一个**有序**数组，每行登记四件事：依赖哪些事实、怎么判（必须是可机械判定的）、不过时给人跑的那一步、通过之后解锁什么能力。
**没登记的机制不算系统的一部分**：机制越加越多时，全貌仍在一张表上，而不是散在代码里。

顺序就是它们成立的顺序：能记账 → 树对不对 → 背景写没写。靠前的错了，后面几条的结论没有意义。

### 13.2 三种结论与"未声明"

- `pass` 通过；`fail` 未通过（附一句缺什么，和一条修法）；`na` 不适用。
- 工作区没被声明成项目时，项目级的检查一律 `na`——**不适用不算未结项**，状态里只显示"没有声明（工作区模式）"。
- 状态是算出来的：`k/n` 与"已认可"，**会随事实退回去**（树一走样，就掉回 `k-1`）。它不是徽章。

### 13.3 声明进账本，认可不进

"这个工作区是一个项目"是账本事实（`project.declare`：形态、背景、每层的目录与依赖方向），可以改，旧的那份留在历史里。
"通过了几条"是投影，不落盘——写进账本就是又一份会过期的当前状态。

### 13.4 它不挡三种状态

未通过不是罢工：轮次、题、任务、交付、送审、判决、签收在任何状态下都能做。体检管的是**项目级能力**（结构约束、条目与交付的绑定、期审拿背景当尺子），不是整个系统。
所以它也不是签收条件：签收只判"这一期做完没有"。

### 13.5 第一批三条

| 检查 | 判什么 | 通过后解锁 |
|---|---|---|
| 账本可读、审查设置已声明 | 账本里有会话、有审查设置（重放本身在到达这里之前就要求成立） | 三种状态与账本 |
| 文件树符合声明的结构 | ①范式要求的格都在（软件：core/app/tests）；②声明的目录在盘上；③盘上每个顶层目录都有归属（认领或写进 `extras`）；④跨格 import 的方向都在 `mayImport` 里 | 结构约束 |
| 项目背景已写 | 背景不是空话 | 项目级验收 |

**格与目录是两个名字**：`layers` 的每条写 `role=dir`——`role` 是范式里的格（`core`/`app`/`tests`…），`dir` 是这个项目实际用的目录名（deed 自己就是 `core=core:,app=cli:…,tests=test:…`）。不写 `role` 时按目录名算。
**没归属的顶层目录**要么认领成某一格，要么写进 `extras`（"它不参与结构"）；两者都不做就是结构里的一块野地。

其余六条（名字已登记、对外契约已声明、条目覆盖、过程材料入口、测试基座、以及"从零开始"的启动路径）**先写着、不实现**：表是数据，不是代码分支，每轮点亮一条。
